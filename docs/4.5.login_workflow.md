The GUI connects to the Lex-Legal FastAPI server on port 8008. The API then connects to Keycloak on port 9090.

```

      participant Template as login.html
      participant View as LoginView.vue
      participant Auth as services/auth.ts
      participant API as Lex-Legal API :8008
      participant Endpoint as authentication.py
      participant Keycloak as Keycloak :9090
      participant JWT as keycloak_auth/auth.py

      Template->>View: submit()
      View->>Auth: login(username, password)
      Auth->>API: OPTIONS /api/auth/login
      API-->>Auth: CORS accepted
      Auth->>API: POST /api/auth/login
      API->>Endpoint: login(LoginRequest)
      Endpoint->>Keycloak: POST token endpoint
      Keycloak-->>Endpoint: Access and refresh tokens
      Endpoint->>JWT: identity_for_token()
      JWT->>Keycloak: Retrieve JWKS signing key when not cached
      JWT-->>Endpoint: Verified claims
      Endpoint-->>Auth: Token, expiry and user identity
      Auth->>Auth: saveAuthentication()
      Auth-->>View: SessionUser
      View->>Router: router.replace(destination)
      Router->>Query: Mount Legal Compliance page
      Query->>API: GET /api/query/conversations
```

  ## 1. Browser opens the Vue application

  The Vue application starts in lex-legal_frontend/src/main.ts:1:

  createApp(App).use(router).mount('#app')

  This:

  1. Creates the Vue application.
  2. Installs the Vue router.
  3. Mounts everything inside the HTML element with ID app.

  ## 2. Router detects that login is required

  The protected Legal Compliance route is defined in lex-legal_frontend/src/router.ts:27:

  {
    path: '/legal-compliance',
    component: QueryView,
    meta: {
      requiresAuth: true,
    },
  }

  The router.beforeEach() guard calls:

  await restoreAuthentication()

  If the user is not authenticated, it redirects to:

  /login?redirect=/legal-compliance

  The redirect value tells the login page where to go after successful authentication.

  ## 3. User submits the login form

  The form is defined in lex-legal_frontend/templates/login.html:22:

  <form class="login-form" @submit.prevent="submit">

  The important parts are:

  - @submit calls the Vue submit() function.
  - .prevent prevents the browser from performing a normal HTML form submission.
  - v-model="username" and v-model="password" connect the inputs to Vue variables.

  Clicking the button therefore calls submit() in lex-legal_frontend/src/views/LoginView.vue:32.


  ## 4. LoginView.vue calls the authentication service

  The submit() function:

  const user = await login(username.value, password.value)

  It performs the following work:

  1. Rejects empty credentials.
  2. Sets submitting = true.
  3. Changes the button text to Signing in….
  4. Calls login() from services/auth.ts.
  5. Waits for the server response.
  6. Redirects the user after success.
  7. Displays the server error after failure.

  The destination is selected by:

  destinationFor(user.is_admin)

  A standard user is redirected to /legal-compliance. An administrator can continue to an administrator-only requested page.

  ## 5. auth.ts creates the HTTP request

  The login() function is in lex-legal_frontend/src/services/auth.ts:66:

  const response = await fetch(`${apiBase}/api/auth/login`, {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({
      username: username.trim(),
      password,
    }),
  })

  The API address comes from lex-legal_frontend/src/services/api.ts:4:

  export const apiBase = (
    import.meta.env.VITE_API_BASE_URL
    || `${protocol}//${browserHost}:8008`
  )

  In Docker, it is configured as:

  VITE_API_BASE_URL=http://10.22.12.250:8008

  Therefore, the browser sends:

  POST http://10.22.12.250:8008/api/auth/login
  Content-Type: application/json

  {
    "username": "reader",
    "password": "password"
  }

  Because ports 5176 and 8008 are different origins, the browser may first send:

  OPTIONS /api/auth/login

  The CORS middleware accepts that request.

  ## 6. FastAPI selects the authentication router

  The unified application is created in app/api/lex_legal_api.py:46.

  The authentication router is registered using:

  app.include_router(
      auth_router,
      prefix="/api",
  )

  The authentication router itself has:

  auth_router = APIRouter(prefix="/auth")

  The login endpoint has:

  @auth_router.post("/login")

  FastAPI combines these three path components:

  /api + /auth + /login

  The resulting endpoint is:

  POST /api/auth/login

  ## 7. authentication.py receives the credentials

  FastAPI converts the JSON body into LoginRequest in app/api/authentication.py:102:

  class LoginRequest(BaseModel):
      username: str
      password: str

  It then calls the endpoint function:

  async def login(request: LoginRequest)

  The function:

  1. Trims and validates the username.
  2. Reads the Keycloak configuration.
  3. Builds a form-encoded Keycloak request.
  4. Calls Keycloak using httpx.AsyncClient.

  The request data is:

  form_data = {
      "client_id": "lex-legal-web",
      "grant_type": "password",
      "scope": "openid profile email",
      "username": username,
      "password": request.password,
  }

  The user’s password is used only for this request and is not written to MongoDB or browser storage.

  ## 8. Backend connects to Keycloak

  The backend calls:

  http://10.22.12.250:9090/realms/dips_services/protocol/openid-connect/token

  The function call is:

  response = await client.post(
      settings.token_url,
      data=form_data,
  )

  Keycloak then:

  1. Finds the user in the dips_services realm.
  2. Checks the password.
  3. Checks whether the lex-legal-web client permits the password grant.
  4. Generates an access token.
  5. Generates a refresh token.
  6. Returns token expiration information.

  If the credentials are invalid, Keycloak returns an error and Lex-Legal converts it into:

  401 Unauthorized

  ## 9. Lex-Legal validates the returned token

  After receiving the token, authentication.py calls:

  identity = identity_for_token(access_token)

  That calls decode_keycloak_token() in keycloak_auth/auth.py:20.

  The validation sequence is:

  identity_for_token()
      └── decode_keycloak_token()
            ├── get_jwks_client()
            ├── get_signing_key_from_jwt()
            └── jwt.decode()

  get_jwks_client() connects to Keycloak’s JWKS endpoint when the signing keys are not already cached:

  /realms/dips_services/protocol/openid-connect/certs

  jwt.decode() validates:

  - the token signature;
  - the RS256 algorithm;
  - the Keycloak issuer;
  - the lex-legal-api audience;
  - token expiration.

  ## 10. Claims are converted into a Lex-Legal user

  After validation, identity_from_claims() extracts:

  sub                 → stable Keycloak user ID
  preferred_username  → displayed username
  email               → user email
  realm_access        → realm roles
  resource_access     → client roles
  groups              → Keycloak groups

  It checks whether the roles contain:

  admin
  lexlegal-admin

  Then it creates:

  AuthenticatedUser(
      subject=...,
      username=...,
      email=...,
      roles=...,
      groups=...,
      is_admin=...,
  )

  ## 11. Backend returns the login response

  The endpoint returns:

  {
    "access_token": "...",
    "refresh_token": "...",
    "token_type": "Bearer",
    "expires_in": 300,
    "expires_at": 1786110000000,
    "user": {
      "subject": "keycloak-subject-id",
      "username": "reader",
      "email": "reader@example.org",
      "roles": ["common-user"],
      "groups": [],
      "is_admin": false
    }
  }

  FastAPI serializes the LoginResponse model and sends it back to the browser.

  ## 12. Browser parses and stores the response

  Back in auth.ts, the response passes through:

  parseJsonResponse<LoginResponse>(response)

  parseJsonResponse() in api.ts:

  1. Parses the JSON.
  2. Checks response.ok.
  3. Throws an error using detail when the server returned an error.
  4. Returns the typed result after success.

  Then saveAuthentication() stores:

  lexguard_access_token
  lexguard_access_expires_at

  in localStorage.

  It also updates the reactive Vue state:

  authState.status = 'authenticated'
  authState.user = response.user

  The refresh token is currently returned by the backend but not stored or used by the frontend.

  ## 13. Vue redirects to Legal Compliance

  LoginView.submit() receives the user and executes:

  await router.replace(destinationFor(user.is_admin))

  For an ordinary user who clicked Open Legal Query, the destination is:

  /legal-compliance

  The router guard runs again. This time restoreAuthentication() immediately sees an authenticated user and permits the navigation.

  ## 14. Legal Compliance starts loading conversations

  Vue mounts QueryView.vue, which calls:

  onMounted(initializeConversations)

  The page then calls:

  GET /api/query/conversations?limit=100
  Authorization: Bearer <access-token>

  authenticatedFetch() automatically adds the bearer token:

  Authorization: `Bearer ${authState.token}`

  FastAPI calls require_authenticated_user(), validates the token again, extracts the Keycloak subject, and returns only conversations owned by that subject.

  The CHATS sidebar then appears, and the user can continue an existing conversation or create a new one.

### 1. Login form submission

  lex-legal_frontend/src/views/LoginView.vue calls:

  login(username, password)

  The sign-in button is disabled while the request is running.

  ### 2. Frontend calls Lex-Legal

  lex-legal_frontend/src/services/auth.ts sends:

  POST http://10.22.12.250:8008/api/auth/login
  Content-Type: application/json

  {
    "username": "your-username",
    "password": "your-password"
  }

  ### 3. Backend calls Keycloak

  app/api/authentication.py forwards the credentials to:

  POST http://10.22.12.250:9090/realms/dips_services/protocol/openid-connect/token
  Content-Type: application/x-www-form-urlencoded

  With approximately:

  client_id=lex-legal-web
  grant_type=password
  scope=openid profile email
  username=<username>
  password=<password>

  The password is not stored by Lex-Legal.

  ### 4. Keycloak returns tokens

  Keycloak returns:

  {
    "access_token": "...",
    "refresh_token": "...",
    "expires_in": 300,
    "token_type": "Bearer"
  }

  Currently, expires_in is 300 seconds—five minutes.

  ### 5. Lex-Legal validates the token

  The backend verifies:

  - JWT signature using Keycloak JWKS;
  - issuer is the dips_services realm;
  - audience is lex-legal-api;
  - token expiration;
  - configured signing algorithm.

  It then extracts:

  - Keycloak subject ID;
  - username and email;
  - realm and client roles;
  - groups;
  - whether the user has admin or lexlegal-admin.

  ### 6. Backend returns the authenticated identity

  Lex-Legal responds with:

  {
    "access_token": "...",
    "refresh_token": "...",
    "token_type": "Bearer",
    "expires_in": 300,
    "expires_at": 1786110000000,
    "user": {
      "subject": "keycloak-user-id",
      "username": "reader",
      "email": "reader@example.org",
      "roles": ["common-user"],
      "groups": [],
      "is_admin": false
    }
  }

  ### 7. Frontend saves authentication

  The frontend currently stores:

  lexguard_access_token
  lexguard_access_expires_at

  in browser localStorage.

  Although the backend returns a refresh token, the frontend currently does not save or use it.

  ### 8. User is redirected

  The original requested URL is preserved in:

  /login?redirect=/legal-compliance

  After successful login:

  - standard users can open /legal-compliance;
  - administrators can also open /import and /legal-query-monitor;
  - a standard user requesting an administrator page is redirected to /legal-compliance.

  ### 9. Subsequent protected requests

  Every protected API request includes:

  Authorization: Bearer <access-token>

  For example:

  GET /api/query/conversations
  Authorization: Bearer <access-token>

  The backend validates the token again before returning conversations or running a legal query.

  If the token is expired, the API returns 401; the frontend clears authentication and redirects to the login page.
