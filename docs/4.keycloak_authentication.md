# Keycloak Authentication and Role-Based Access

## Access model

The public overview page remains available without authentication. Clicking a
protected destination redirects the user to `/login` and returns them to the
requested page after successful authentication when their role permits it.

| Page or API | Common authenticated user | Administrator |
|---|---:|---:|
| Overview `/` | Yes | Yes |
| Legal Compliance `/legal-compliance` | Yes | Yes |
| Knowledge Import `/import` | No | Yes |
| Query Monitor `/legal-query-monitor` | No | Yes |
| Query/history/stream APIs | Yes | Yes |
| Import upload/status APIs | No | Yes |

Administrator roles are configured with:

```env
LEXLEGAL_ADMIN_ROLES=admin,lexlegal-admin
```

Role comparison is case-insensitive. Roles may come from Keycloak realm roles
or client roles belonging to `lex-legal-web` or `lex-legal-api`. Roles from an
unrelated Keycloak client are ignored, preventing accidental privilege reuse
across applications.

## Keycloak clients

Lex-Legal uses two Keycloak clients:

- `lex-legal-web`: login client used to exchange username/password credentials;
- `lex-legal-api`: protected API audience used during token verification.

Required Keycloak configuration:

1. Create or retain the public client `lex-legal-web`.
2. Enable Direct Access Grants for `lex-legal-web`, because the current custom
   login page uses the password grant through the backend.
3. Create or retain `lex-legal-api` as the API resource client.
4. Add an audience mapper to `lex-legal-web` so issued access tokens contain
   `lex-legal-api` in the `aud` claim.
5. Assign ordinary accounts any normal user role.
6. Assign administrators either `admin` or `lexlegal-admin`, or change
   `LEXLEGAL_ADMIN_ROLES` to the desired role names.

Without the audience mapper, username/password authentication may succeed at
Keycloak but Lex-Legal will reject the resulting token because it was not
issued for `lex-legal-api`.

## Environment

Host development defaults:

```env
KEYCLOAK_ISSUER=http://127.0.0.1:9090/realms/dips_services
KEYCLOAK_JWKS_URL=http://127.0.0.1:9090/realms/dips_services/protocol/openid-connect/certs
KEYCLOAK_TOKEN_URL=http://127.0.0.1:9090/realms/dips_services/protocol/openid-connect/token
KEYCLOAK_CLIENT_ID=lex-legal-api
KEYCLOAK_AUDIENCE=lex-legal-api
KEYCLOAK_LOGIN_CLIENT_ID=lex-legal-web
KEYCLOAK_LOGIN_CLIENT_SECRET=
KEYCLOAK_ALGORITHMS=RS256
LEXLEGAL_ADMIN_ROLES=admin,lexlegal-admin
```

The shared Docker Compose file supplies equivalent URLs based on `HOST_ADDR`.

## Backend flow

```text
POST /api/auth/login
  -> Query API sends credentials to the Keycloak token endpoint
  -> Keycloak returns an access token
  -> Query API verifies signature, issuer, expiry, and lex-legal-api audience
  -> Query API maps roles and returns token plus normalized user information
```

Protected requests use:

```http
Authorization: Bearer <access-token>
```

The Query API uses `require_authenticated_user`. The Import API uses
`require_admin_user`, so a common user receives HTTP 403 even if they manually
call the upload endpoint.

Health endpoints remain public for Docker health checks.

## Frontend flow

The Vue router marks Legal Compliance as authenticated and Import/Monitor as
administrator-only. The original index page is unchanged and remains public.

The browser stores the access token and expiration time in local storage,
restores it through `GET /api/auth/me`, clears it on logout or HTTP 401, and never
stores the password. Logout and token expiry also remove the browser's current
conversation ID and local monitor records, preventing data from one account
from appearing when another account later uses the same browser.

The SSE query stream is consumed with authenticated `fetch`, not native
`EventSource`. This keeps the bearer token in the Authorization header and out
of URLs, browser history, proxy logs, and query strings.
