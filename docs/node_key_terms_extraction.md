# `node_key_terms_extraction` Technical Note

## Purpose

`node_key_terms_extraction` enriches searchable legal child chunks with concise
legal key terms generated by an LLM.

The node is located at:

```text
app/import_process/agent/nodes/node_key_terms_extraction.py
```

Key terms are retrieval metadata. They help Elasticsearch keyword matching and
future retrieval features recognize important legal concepts, but they do not
replace or modify the authoritative legal text.

The central rule is:

> Extract legal concepts from child text, preserve the original text, and never
> allow optional keyword enrichment to stop document ingestion.

## Position in the Import Workflow

```text
node_document_split
    -> creates legal parent and child records

node_key_terms_extraction
    -> extracts and validates terms for child records
    -> writes chunks_with_keywords.json

node_import_es
    -> stores parents and enriched children

node_bge_embedding
    -> embeds searchable child text

node_import_milvus
    -> stores child vectors and filtering metadata
```

## Why Only Child Chunks Are Enriched

The legal splitter creates two record levels:

```text
parent
    -> complete Article, recital group, or Annex

child
    -> paragraph, point group, definition group, or individual recital
```

Children are the primary retrieval units. Extracting terms from complete parent
Articles would:

- duplicate terms across parent and child records;
- increase LLM calls and token usage;
- produce broader and less precise concepts;
- add metadata to records that are mainly used for context expansion.

The node therefore selects records where:

```python
chunk["record_type"] == "child"
```

The child must also contain non-empty text and must not already contain usable
key terms.

## Input Contract

The node reads:

```python
state["task_id"]
state["chunks"]
state["local_dir"]
state["md_path"]
```

`state["chunks"]` must be a non-empty list of dictionaries produced by
`node_document_split`.

Example child:

```json
{
  "chunk_id": "gdpr:article_6:paragraph_1_points_d_f",
  "parent_id": "gdpr:article_6",
  "law_id": "gdpr",
  "record_type": "child",
  "content_type": "article",
  "article_number": "6",
  "article_title": "Lawfulness of processing",
  "text": "Processing shall be lawful only if...",
  "key_terms": []
}
```

Parent records remain in the list but are not sent to the LLM.

## Output Contract

The node updates and returns the graph state:

```python
state["chunks"] = chunks
```

Successful child example:

```json
{
  "chunk_id": "gdpr:article_6:paragraph_1_points_d_f",
  "record_type": "child",
  "text": "Processing shall be lawful only if...",
  "key_terms": [
    "legitimate interests",
    "fundamental rights and freedoms",
    "data subject"
  ]
}
```

The node also writes:

```text
state["local_dir"]/chunks_with_keywords.json
```

If `local_dir` is absent, the backup is written beside `md_path`.

## Main Execution Steps

### Step 1: Select chunks requiring extraction

```python
step_1_get_chunks_for_extraction(state)
```

This function:

1. validates that `state["chunks"]` is a non-empty list;
2. validates that every item is a dictionary;
3. normalizes any existing `key_terms`;
4. selects child records with non-empty text;
5. skips children that already contain usable terms;
6. validates that selected children contain `chunk_id`.

Existing terms are normalized even when no new LLM call is required. This
removes obsolete citation-heavy values from older backup files.

The skip behavior makes the node idempotent:

```text
first run
    -> extracts missing terms

second run
    -> preserves existing terms
    -> avoids unnecessary LLM calls
```

### Step 2: Build the LLM request

```python
_build_user_prompt(batch)
```

Only fields useful for extraction are sent:

```json
{
  "chunk_id": "...",
  "content_type": "article",
  "article_number": "6",
  "article_title": "Lawfulness of processing",
  "text": "..."
}
```

Fields such as vectors, storage paths, and unrelated metadata are excluded to
keep prompts smaller.

The model must return:

```json
{
  "chunks": [
    {
      "chunk_id": "unchanged input ID",
      "key_terms": [
        "legal concept"
      ]
    }
  ]
}
```

The node matches results by `chunk_id`. It does not assume that the LLM keeps
the original input order.

### Step 3: Validate and normalize the response

```python
step_2_extract_batch_key_terms(llm_client, batch)
```

The function:

- parses provider text or content-block output;
- tolerates an accidental outer Markdown JSON fence;
- requires a JSON object containing a `chunks` list;
- ignores malformed response items;
- ignores invented chunk IDs;
- ignores duplicate results for the same ID;
- normalizes every `key_terms` list;
- returns both valid results and omitted IDs.

Return shape:

```python
(
    {
        "chunk_id_1": ["term one", "term two"],
        "chunk_id_2": [],
    },
    {"omitted_chunk_id"},
)
```

An explicit empty list is a valid result. It means the model found no useful
legal term. An omitted ID is different and must be retried.

## Key-Term Quality Rules

The system prompt asks the model to prefer:

- exact legal phrases;
- regulated entities;
- rights and duties;
- legal tests;
- procedures;
- exceptions;
- defined terms.

Examples of useful terms:

```text
legitimate interests
data subject access rights
controller obligations
public sector body
data intermediation services
fundamental rights and freedoms
```

The prompt forbids:

- generic standalone words;
- legal citations;
- instrument identifiers;
- Article, recital, and paragraph references;
- dates and years;
- deadlines and durations;
- numbered ranges;
- formal titles of cited legislation.

Examples rejected by the prompt and local validation:

```text
Directive (EU) 2016/680
Directive 2000/31/EC
Articles 12 to 15
Article 6
Recital 42
26 April 2016
30 days
```

## Local Term Validation

```python
_normalise_key_terms(value)
```

Local validation protects downstream storage even when the LLM ignores prompt
rules.

It:

- requires a list;
- accepts only strings;
- collapses repeated whitespace;
- removes surrounding punctuation;
- rejects empty terms;
- rejects terms longer than `MAX_KEY_TERM_LENGTH`;
- rejects every term containing a digit;
- rejects legal-location words such as `Article` or `paragraph`;
- deduplicates terms case-insensitively;
- limits output to `MAX_KEY_TERMS`.

Current limits:

```python
MAX_KEY_TERMS = 8
MAX_KEY_TERM_LENGTH = 100
```

## Batch and Retry Strategy

Normal extraction uses:

```python
KEYWORD_BATCH_SIZE = 8
```

Batching reduces API overhead compared with one request per child.

An LLM may occasionally return only part of a batch. For example:

```text
input:  8 chunk IDs
output: 6 chunk IDs
missing: final 2 chunk IDs
```

The previous behavior rejected all eight results. The current behavior
preserves the six valid results and retries only the two missing chunks.

### Retry rounds

```text
Round 1
    -> send the normal batch of up to 8 chunks

Round 2
    -> send unresolved chunks in groups of 2

Round 3
    -> send each still-unresolved chunk individually
```

Configuration:

```python
KEYWORD_RETRY_BATCH_SIZE = 2
MAX_KEYWORD_EXTRACTION_ATTEMPTS = 3
```

The coordinator is:

```python
_extract_batch_with_retries(...)
```

It never resends chunks that already produced a valid response. This reduces
cost and prevents successful values from being replaced unnecessarily.

### Why bounded retries are important

An unbounded retry loop could:

- block the import workflow indefinitely;
- repeatedly spend LLM tokens;
- overload the model service;
- prevent later document batches from running.

Three progressively smaller rounds provide a practical recovery strategy while
keeping runtime predictable.

## Detecting Truncated Responses

The node logs provider response metadata when available:

```python
response.response_metadata
```

Important value:

```text
finish_reason = "length"
```

This usually indicates that the response reached the model's output-token
limit. The smaller retry requests reduce the output required from the model.

Other providers may expose the same information as:

```text
stop_reason
```

Metadata logging is diagnostic only; retry behavior does not depend on one
specific provider.

## Failure Behavior

Key-term extraction is an optional retrieval enhancement. The original legal
text remains authoritative.

If some chunks still fail after all retries:

```text
successful chunks
    -> keep their extracted terms

unresolved chunks
    -> retain key_terms: []

later batches
    -> continue processing

document ingestion
    -> continues to Elasticsearch and Milvus
```

The final warning includes only IDs still unresolved after all retry rounds.

This means:

- the legal document is not lost;
- Elasticsearch still stores its text;
- Milvus still stores its dense vectors;
- BM25 text retrieval still works;
- semantic retrieval still works;
- only keyword-based boosting is weaker for unresolved chunks.

## Backup File

```python
step_4_backup_chunks_with_keywords(...)
```

The node always creates:

```text
chunks_with_keywords.json
```

The backup includes:

- parents with unchanged empty terms;
- successfully enriched children;
- children with an explicit empty result;
- unresolved children that remained empty after retries.

This file is intended for inspection and debugging before records are imported
into Elasticsearch.

## Operational Guidance

If omitted IDs occur occasionally:

```text
No immediate action is required.
The targeted retry mechanism should recover them.
```

If omitted IDs occur frequently:

1. inspect `finish_reason`;
2. check the model's output-token limit;
3. check LLM service load and timeout logs;
4. consider reducing `KEYWORD_BATCH_SIZE`;
5. verify that chunk text is not unexpectedly large;
6. inspect `chunks_with_keywords.json`.

If the model is overloaded, retries in this node do not currently add a sleep
or exponential backoff. Service-overload retries should be added separately
with bounded delays because they solve a different problem from omitted IDs.

## Known Limits

- LLM-generated terms are not authoritative legal evidence.
- Digit rejection may remove a rare meaningful concept that legitimately uses
  a number; this is an intentional retrieval-quality trade-off.
- Terms are generated from each child independently, not from the entire law.
- The node uses synchronous LLM calls inside a synchronous LangGraph node.
- Retry rounds increase LLM requests when responses are incomplete.
- Final unresolved chunks remain searchable through their original text and
  vectors but do not receive key-term enhancement.
