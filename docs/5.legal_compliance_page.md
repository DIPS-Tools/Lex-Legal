# Legal Compliance Page

## 1. Purpose

The Legal Compliance page is the authenticated chat workspace for ordinary
legal questions and policy-compliance assessments. It combines the Lex-Legal
query workflow with persistent, user-owned conversations.

Users can:

- start a new legal conversation;
- submit legal questions or policies for compliance assessment;
- receive synchronous or streamed answers;
- review previous conversations in the CHATS sidebar;
- reopen a conversation and continue it with its existing context;
- delete conversations they no longer need.

The page is available at:

```text
/legal-compliance
```

It requires a valid Keycloak login. Both standard users and administrators can
access it.

## 2. Page layout

The page contains two main areas.

### 2.1 CHATS sidebar

The left sidebar contains:

- the LexGuard identity;
- the **New conversation** button;
- the authenticated user's saved conversations;
- a delete control for each conversation;
- the active-session indicator.

The selected conversation is visually highlighted. Long conversation titles
are truncated in the sidebar, while the complete title remains available as a
tooltip.

### 2.2 Conversation workspace

The main workspace contains:

- the active conversation title;
- the response-streaming switch;
- chronological user and assistant messages;
- retrieval progress for a running query;
- Markdown-rendered legal answers;
- referenced legal-document images, when present;
- the legal-query input and send button.

Assistant Markdown is sanitized before being inserted into the page.

## 3. Conversation lifecycle

### 3.1 Opening the page

When the page opens, the frontend requests the current user's conversations:

```http
GET /api/query/conversations?limit=100
```

The page then:

1. Reopens the conversation stored in `lexguard_session_id` when it still
   belongs to the current user.
2. Otherwise opens the most recently active conversation.
3. Creates a new conversation when the user has no saved conversations.
4. Loads the selected conversation's messages from MongoDB.

### 3.2 Starting a new conversation

Clicking **New conversation** calls:

```http
POST /api/query/conversations
Content-Type: application/json

{}
```

The API creates a server-generated session ID such as:

```text
legal-96ecdf5e-5d6a-4733-a57f-8792b30e6652
```

The initial title is `New conversation`. After the first query is submitted,
the API derives a compact title from that query. Titles are normalized to one
line and limited to 72 characters.

Creating a new conversation does not clear or overwrite earlier sessions.

### 3.3 Submitting a query

The frontend sends the active session ID with every request:

```http
POST /api/query
Content-Type: application/json
Authorization: Bearer <access-token>

{
  "query": "Does this retention policy comply with the GDPR?",
  "session_id": "legal-96ecdf5e-5d6a-4733-a57f-8792b30e6652",
  "is_stream": true
}
```

Before starting the LangGraph workflow, the API verifies that the session
belongs to the authenticated Keycloak subject. It also updates the
conversation's `updated_at` timestamp, causing the conversation to move to the
top of the CHATS list.

The query graph continues to store the user and assistant messages in the
existing `chat_message` collection. Consequently, follow-up questions can use
the previous turns as conversation context.

### 3.4 Reopening a conversation

Clicking an item in CHATS changes the active session and requests its history:

```http
GET /api/query/history/{session_id}?limit=100
```

The returned messages are displayed chronologically. New queries continue
using the same `session_id`, so the legal intent and answer nodes can load the
earlier context from MongoDB.

The application does not copy messages into a new session when reopening a
chat.

### 3.5 Deleting a conversation

The × control asks the user for confirmation and then calls:

```http
DELETE /api/query/conversations/{session_id}
```

Deletion removes:

- the conversation metadata from `chat_conversation`;
- every matching message from `chat_message`.

If the active conversation is deleted, the page opens the next most recent
conversation. If no conversations remain, it creates a new one automatically.

## 4. MongoDB representation

Conversation metadata and messages are kept in separate collections.

### 4.1 `chat_conversation`

Example record:

```json
{
  "session_id": "legal-96ecdf5e-5d6a-4733-a57f-8792b30e6652",
  "owner_id": "keycloak-subject-id",
  "title": "Does this retention policy comply with the GDPR?",
  "title_is_default": false,
  "created_at": "2026-08-07T13:20:00+00:00",
  "updated_at": "2026-08-07T13:25:00+00:00"
}
```

Indexes:

- unique `session_id`;
- compound `owner_id, updated_at DESC` for the CHATS list.

### 4.2 `chat_message`

Example record:

```json
{
  "session_id": "legal-96ecdf5e-5d6a-4733-a57f-8792b30e6652",
  "role": "user",
  "text": "Does this retention policy comply with the GDPR?",
  "rewritten_query": "Assess the retention policy against applicable GDPR requirements.",
  "query_key_terms": ["GDPR", "retention period", "storage limitation"],
  "image_urls": [],
  "ts": "2026-08-07T13:25:00+00:00"
}
```

Messages remain ordered by the existing `session_id, ts DESC` index.

## 5. API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| `GET` | `/api/query/conversations` | List the current user's conversations |
| `POST` | `/api/query/conversations` | Create a new conversation |
| `DELETE` | `/api/query/conversations/{session_id}` | Delete an owned conversation and its messages |
| `POST` | `/api/query` | Submit a query using the active session |
| `GET` | `/api/query/stream/{session_id}` | Receive SSE progress and answer events |
| `GET` | `/api/query/history/{session_id}` | Load an owned conversation's messages |
| `DELETE` | `/api/query/history/{session_id}` | Clear messages while retaining conversation metadata |

These endpoints appear under **Legal Compliance APIs** in the unified Swagger
UI:

```text
http://localhost:8008/docs
```

## 6. Authentication and ownership

Conversation ownership uses the stable Keycloak `sub` claim, not the displayed
username. Usernames and email addresses can change, while the subject ID is the
identity represented by the access token.

Ownership is checked before:

- submitting a query to an existing session;
- connecting to its SSE stream;
- reading its history;
- clearing its history;
- deleting the conversation.

An unknown session and a session belonging to another user both return:

```http
404 Not Found
```

Using the same response prevents the API from revealing whether another user's
session ID exists.

Administrators do not automatically receive access to other users'
conversations. Administrator privileges apply to document import and monitor
pages, while chat ownership remains private to the conversation owner.

## 7. Streaming behavior

When streaming is enabled:

1. `POST /api/query` validates or creates the conversation metadata.
2. The API creates the session's in-memory SSE queue.
3. The query graph starts as a background task.
4. The browser opens `/api/query/stream/{session_id}`.
5. The page displays progress, token deltas, the final answer, or an error.

The CHATS controls are disabled while the current query is running. This avoids
switching or deleting the active session while its stream is still being
processed.

## 8. Persistence and compatibility

Conversation lists are server-backed and therefore survive:

- browser refreshes;
- closing and reopening the browser;
- logging out and logging in again;
- using another browser after authenticating as the same Keycloak user.

`localStorage` contains only the most recently selected session ID. It is a UI
preference, not the authoritative conversation store.

Messages created before conversation ownership was introduced do not contain
enough information to determine their Keycloak owner safely. Those legacy
sessions are therefore not automatically displayed in CHATS. Conversations
created by the new page include ownership metadata from the beginning.
